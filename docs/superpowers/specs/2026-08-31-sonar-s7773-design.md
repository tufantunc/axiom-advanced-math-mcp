# SonarQube S7773 — Number static methods over global equivalents

Date: 2026-08-31
Branch: `fix/sonarqube` (from `origin/main` b57af28)
Rule: `typescript:S7773` — Number static methods and properties should be
preferred over global equivalents.

## Problem

The SonarQube project `axiom-math` reports 74 S7773 findings against this repo
(Aug 21 scan). A fresh audit of `origin/main` finds **65 code sites** in
`src/**/*.ts` across ~19 files (the delta is scan drift — main moved since
Aug 21; `test/` contains no sites):

| Global | Sites | Replacement |
|---|---|---|
| `parseInt` | 19 | `Number.parseInt` |
| `parseFloat` | 20 | `Number.parseFloat` |
| `isNaN` | 19 | `Number.isNaN` |
| `isFinite` | 5 | `Number.isFinite` |
| `NaN` (assignment) | 2 | `Number.NaN` |

Out of scope: comments (`src/http.ts:10` mentions `parseInt` in prose), string
literals, and regex literals (`src/server/tools/compute/silent-failure.ts:22`
matches `NaN` in Giac output text — must keep matching).

## Semantic safety argument

- `parseInt`/`parseFloat`: the globals ARE `Number.parseInt`/`Number.parseFloat`
  per spec — identical functions. Zero risk.
- `NaN` assignments (`hypothesis-testing.ts:161,209`): `Number.NaN` is the same
  value. Zero risk.
- `isNaN`/`isFinite` are the only semantic fork: the globals coerce their
  argument (`isNaN('abc') === true`), the Number versions require a number
  (`Number.isNaN('abc') === false`). **All 24 sites in this repo pass a
  statically-`number` argument** — a `parseFloat`/`parseInt` result, a
  `number`-typed parameter, or a value narrowed by `typeof x === 'number'` —
  where both families behave identically. Verified site-by-site during design
  (see worktree exploration 2026-08-31); the implementation re-verifies via
  typecheck.

This repo's own trap list ("a silent wrong answer is the worst failure") makes
the argument above the load-bearing part of this change: no site may swap a
possibly-non-number argument.

## Approach (chosen: lint rule + autofix)

**A. Enable `unicorn/prefer-number-properties` in oxlint, autofix via
`npm run lint:fix`** — chosen. AST-aware (cannot touch comments, strings, or
regex literals), fast, and the rule stays enabled afterwards as a permanent
regression guard so S7773 cannot re-enter the codebase.

Rejected:
- **B. Manual edits** — same result, slower, no permanent guard.
- **C. sed codemod** — text-based; would corrupt the `http.ts` comment and the
  `silent-failure.ts` regex. Unsafe.

## Approved design details

1. `.oxlintrc.json`: `plugins` becomes `["typescript", "unicorn"]`; add
   `"unicorn/prefer-number-properties": "warn"`. The rule remains enabled after
   the fix lands (guard).
2. Run `npm run lint:fix`; review the diff — expected changes are exclusively
   `Number.`-prefix additions and the two compound collapses below.
3. Compound checks collapse to the single equivalent call (user-approved):
   - `src/server/tools/response-formatter.ts:29`:
     `!isNaN(rounded) && isFinite(rounded)` → `Number.isFinite(rounded)`
   - `src/server/tools/verify/index.ts:196`:
     `isNaN(numResult) || !isFinite(numResult)` → `!Number.isFinite(numResult)`
   For `number`-typed arguments both forms are mathematically identical
   (`Number.isFinite` is false for `NaN` and `±Infinity`).
4. Verification: `npm run typecheck`, `npm run lint`, `npm test` (758 unit
   tests), plus `npm run test:integration` for belt-and-braces. All must pass
   before commit.
5. Single commit: `refactor: prefer Number static methods over globals (S7773)`
   including the `.oxlintrc.json` change. The design doc is a separate commit
   made before implementation.

## Error handling

If autofix leaves any residual warning (not expected), finish those sites
manually before verification. `src/server/giac/giac.wasm.js` is already in
oxlint's `ignorePatterns` and is out of scope.
