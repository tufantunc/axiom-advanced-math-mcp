# GLM-5.1 Failure Triage — Methodology Design

**Date:** 2026-06-09
**Branch:** `glm5-failure-triage` (isolated worktree)
**Status:** DESIGN — approved, pending implementation plan
**Type:** Read-only analysis (no production code changes)

## Background

The "push the CAS verification pipeline" arc shipped three tiers (Tier 1 output
hygiene, Tier 2 self-verification, Tier 3 input normalization). Before deciding
what to build next, we need to know **why GLM-5.1 fails the problems it fails** —
and how much of that is addressable by tooling versus model/CAS-capability bound.
This was deferred during the tier work; now we run it.

Per the earlier analysis, the only honest way to size "what's worth building" is
to bucket the actual failures rather than guess.

## Goal

Classify GLM-5.1's tool-augmented failures on the existing benchmark traces into
three buckets, cross-reference each tool-addressable failure against the three
tiers we already shipped, and produce an evidence-based recommendation for what
(if anything) to build next.

**Non-goals:** running new benchmarks (this uses existing traces); changing
production code; measuring accuracy lift (a separate, later targeted re-run).

## Inputs

Existing `*-details.jsonl` traces in `benchmark/results/` (gitignored, so read
from the main checkout path `/Users/tufantunc/Desktop/Projects/Personal/axiom-advanced-math-mcp/benchmark/results/`):

- **CAS-quick** (60 problems): the band Tier 1/2/3 targeted (~70% ceiling, ~18 failures).
- **olympiad-quick** (Omni-MATH ≥7, ~50 problems): characterizes the capability wall (~48 failures).

Use the most recent run per dataset. Each record has:
`{ question, groundTruth, baseline, toolAugmented{ extractedAnswer, correct, method, toolCalls[{name,args,result}] }, regression, improvement }`.

**Failure set:** records where `toolAugmented.correct === false`.

**Caveat (must be stated in findings):** these traces predate Tier 1/2/3, so they
reflect the OLD tool behavior. That is exactly why the tier cross-reference below
matters — it tells us how many of these old failures our shipped work already
fixes.

## Bucket definitions + detection signals

Each failure is assigned exactly one bucket (judgment from reading the trace):

1. **tool-loss** — Giac produced, or could trivially have produced, the correct
   answer, but it was lost in plumbing/extraction.
   - Signals: the tool `result` text contains the groundTruth (or a
     normalized-equal form) while `extractedAnswer` ≠ GT; visible output
     corruption (`micro`, truncated LaTeX, `list[...]`, stray quotes, set
     notation that should have matched).

2. **capable-but-erring** — the model engaged correctly (reasonable
   formalization) but hit a recoverable error a retry/escalation could fix.
   - Signals: `GIAC_ERROR`/`undef`/syntax error in a tool result followed by the
     model giving up or echoing the error; correct intent but wrong method/domain
     (e.g. real `solve` where complex roots were needed); correct tool output but
     a wrong final answer from a downstream reasoning/arithmetic slip.

3. **incapable** — neither the model nor Giac can reach the answer with the
   current stack.
   - Signals: misformalization (tool args do not correspond to the problem);
     Giac genuinely cannot handle the class (geometry constructions,
     existence/proof problems); groundTruth is a proof, long-text, or
     symbolic-in-n answer that does not fit the boxed/numeric format.

**Cross-cutting flag (not a bucket):** `no-tool-call` — the model made zero tool
calls. Reported as a rate per dataset; a no-tool-call failure is still assigned a
bucket (usually `incapable` if the model never recognized the need, or
`capable-but-erring` if the problem was plainly computable).

## Tier cross-reference (the key value-add)

For every `tool-loss` failure (and any `capable-but-erring` failure with a clear
tooling fix), tag whether one of the shipped tiers now addresses it:

- **Tier 1** (output hygiene): series `order_size`/truncation, stray latex quotes,
  `list[...]` → set, boxed fail-safe.
- **Tier 2** (self-verification): real→complex `solve` escalation (complex-only
  roots), the `Verified` confidence signal.
- **Tier 3** (input normalization): unicode glyph corruption (`x²`→`xmicro`, `·`).

Output three sub-totals for the addressable failures:
**already-fixed-by-Tier-1/2/3** vs **remaining-addressable** vs **incapable**.

## Output

A findings doc `docs/superpowers/specs/2026-06-09-glm5.1-failure-triage-results.md`:

- Per-dataset failure counts by bucket (table).
- `no-tool-call` rate and output-corruption count per dataset.
- The tier cross-reference sub-totals (already-fixed / remaining-addressable /
  incapable), with 2-4 representative trace excerpts per category.
- An evidence-based recommendation: is there a `remaining-addressable` bucket big
  enough to justify more tooling, or is the residue overwhelmingly `incapable`
  (→ stop tooling, the honest conclusion the project has trended toward)?

## Execution

Read-only analysis, no production code changes.

- **Two analysis subagents** (one per dataset) read the failure records from the
  main-checkout trace path and return structured per-problem classifications:
  `{ index, question, gt, bucket, tierFix?: 'T1'|'T2'|'T3'|null, noToolCall, oneLineReason }`.
- The controller synthesizes the two structured results into the findings doc,
  computes the counts/sub-totals, and writes the recommendation.

Both the methodology spec and the findings doc are committed on the
`glm5-failure-triage` worktree branch, isolated from the parallel sessions.

## Validity notes

- Classification is judgment-based; the subagents must quote the trace evidence
  (the specific tool result / extracted answer / GT) for each assignment so the
  controller can spot-check.
- Single-rater classification (no adversarial double-rating) — acceptable for a
  scoping triage; borderline cases are flagged rather than forced.
- The pre-tier caveat is stated prominently so the `tool-loss` count is read as
  "the before picture," not the current state.
